1. Resumen del Proyecto

Motor Agéntico es un dashboard local de costos y actividad para agentes de IA. Lee transcripts de Claude Code (~/.claude/projects) y Codex (~/.codex) en solo lectura, calcula el gasto "equivalente API" y señala fugas de tokens.


Principio fundamental: Las fuentes (~/.claude, ~/.codex) son SOLO LECTURA. Todo estado propio vive en ./data/. No usa claves API, binda solo a 127.0.0.1:8081.

Tech stack:

  • Backend: Node.js ≥ 22.5, Fastify, SQLite (node:sqlite experimental)
  • Frontend: React 18, Vite 5, Tailwind CSS 3, Recharts
  • Tests: Vitest (75 tests, 13 suites)
  • Package manager: pnpm 11
  • Lenguaje: TypeScript 5.9 (strict mode)

Flujo de datos

  1. Descubrimiento: Cada adapter encuentra sus transcripts (Claude: *.jsonl, Codex: rollout-*.jsonl)
  2. Ingesta incremental: Solo re-lee líneas nuevas (offset por archivo con size/mtime)
  3. Normalización: Cada adapter convierte a UsageEvent común
  4. Costo: Se calcula en ingesta con costForEvent() usando pricing.json
  5. DB: SQLite con WAL, tablas: sessions, usage_events, skills_usage, memory_nodes, ingest_offsets
  6. API: Endpoints leen de la DB y devuelven JSON

  • Nunca abre auth.json, .env ni credenciales
  • Bind exclusivo a 127.0.0.1
  • Test de integridad: hashea fuentes antes/después de ingesta

  • Separación clara: adapters / lib / server / cli
  • Tipado TypeScript strict sin errores
  • Comentarios explican el por qué, no el qué
  • Dedup por PK en DB + dedup in-memory por archivo

  • Test de integridad (fuentes intactas)

4. Problemas Detectados

🔴 Alto — App.tsx es un monolito de 1002 líneas

Todo el frontend vive en un solo archivo: 7 páginas, tipos, helpers, hooks, componentes. Esto dificulta:

  • Mantenimiento y navegación
  • Code-splitting (todo se carga en un bundle)
  • Testing de componentes individuales
  • Colaboración (conflictos de merge frecuentes)

Archivo: web/src/App.tsx

🔴 Alto — Config.json no tiene el campo waste

data/config.json no incluye el campo waste. Aunque loadConfig() hace merge con defaults (y funciona), el usuario que edite la config desde la UI verá los campos de fugas pero al guardar se persistirá sin ellos si el merge no es correcto en saveConfig.

Archivo: data/config.json + src/lib/config.ts

Impacto: Bajo (el merge lo resuelve), pero inconsistencia entre lo guardado y lo esperado.

🟡 Medio — node:sqlite es experimental

Se carga con createRequire para evitar el bundling, pero la API puede cambiar entre versiones de Node. Los warnings de ExperimentalWarning aparecen en cada test.

Impacto: Funcional pero frágil ante upgrades de Node.

🟡 Medio — Sin validación de input en PUT /api/pricing

El endpoint acepta cualquier JSON y solo valida que tenga models. No valida que las tarifas sean números positivos, que los nombres de modelo sean válidos, etc. Un JSON mal formado puede corromper pricing.json.

Archivo: src/server.ts

🟡 Medio — Memoria: DELETE + INSERT en cada ingesta

refreshMemoryNodes() borra todos los nodos y los reinserta en cada ingesta. Con muchos archivos de memoria esto es ineficiente. No hay incrementalidad para la memoria.

Archivo: src/ingest.ts

🟡 Medio — Import dinámico innecesario en CodexAdapter

CodexAdapter.parseSession() usa await import("../lib/fs-readonly.js") en vez de usar el import estático del inicio del archivo. Es un dynamic import innecesario que añade latencia.

Archivo: src/adapters/codex.ts

🟢 Bajo — Reportes sin limpieza automática

Cada ingesta genera un data/reports/run-<ts>.json. No hay mecanismo de rotación o limpieza. Con el tiempo pueden acumularse cientos de archivos.

🟢 Bajo — Sin graceful shutdown para ingesta larga

Si el servidor se apaga durante una ingesta grande (rebuild con miles de sesiones), la transacción puede quedar a medias. El WAL de SQLite lo protege, pero no hay signal handler para cerrar la DB limpiamente.

6. Sugerencias de Mejora

6.1. Romper el monolito del frontend

Problema: web/src/App.tsx tiene 1002 líneas con 7 páginas, tipos, hooks y componentes.

Solución propuesta:

web/src/
├── App.tsx          ← solo shell + tabs + router
├── types.ts         ← interfaces compartidas
├── hooks.ts         ← useApi, useRefresh
├── components/
│   ├── Panel.tsx
│   ├── Loading.tsx
│   ├── ErrorMsg.tsx
│   └── Legend.tsx
├── pages/
│   ├── Inicio.tsx
│   ├── Ahorro.tsx
│   ├── Skills.tsx
│   ├── Memoria.tsx
│   ├── Actividad.tsx
│   ├── Configuracion.tsx
│   └── Ayuda.tsx
└── utils.ts         ← fmt, compact, pct, usd

6.2. Agregar un linter

No hay eslint ni biome. Agregar biome (rápido, zero-config) para asegurar consistencia de estilo y detectar problemas comunes:

pnpm add -D @biomejs/biome
pnpm biome init
# En package.json:
"lint": "biome check src/ test/ web/src/"

6.3. CI/CD con GitHub Actions

El proyecto tiene .github/ pero no hay workflow de CI. Agregar:

name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - run: pnpm install
      - run: pnpm typecheck
      - run: pnpm test
      - run: pnpm build:web

6.4. Graceful shutdown

Agregar signal handlers en server.ts:

for (const sig of ['SIGTERM', 'SIGINT']) {
  process.on(sig, async () => {
    console.log(`\n${sig} — cerrando...`);
    await app.close();
    db.close();
    process.exit(0);
  });
}

6.5. Validación de pricing

Antes de guardar pricing.json, validar:

  • Cada modelo tiene input y output como números ≥ 0
  • No hay claves vacías
  • Estructura coincide con Pricing interface

6.6. Paginación en /api/activity

Con muchas sesiones, getActivity() devuelve todo sin paginar. Agregar ?page=1&limit=50 y un cursor basado en ended_at.

6.7. Exportar datos

Agregar un endpoint GET /api/export?format=csv|json que exporte sessions + usage_events. Útil para análisis externo o backup.

6.8. Buscador de sesiones

La página de Actividad muestra todas las sesiones por día. Agregar un buscador que filtre por proyecto, modelo, o texto del prompt (leyendo transcripts en demanda).

Resumen ejecutivo

Proyecto sólido y bien diseñado. La arquitectura es limpia, la seguridad está bien pensada, y los 75 tests dan confianza. Los principales puntos de mejora son: descomponer el frontend (App.tsx monolítico), agregar CI/CD, validación de input en endpoints de escritura, y un linter para mantener consistencia. El proyecto está en buena forma para recibir un tercer adapter y features de export/búsqueda.
